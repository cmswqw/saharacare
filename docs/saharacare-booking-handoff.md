### Actual schema and decisions

All six tables live in the existing **unexposed `private` schema**, with RLS enabled and no raw privileges for PUBLIC, anon or authenticated. This avoids exposing internal catalog/review/payment metadata through a table SELECT. Only trusted server `service_role` receives explicit SELECT/INSERT/UPDATE/DELETE on the new tables plus schema USAGE. No broad GRANT ALL, browser privilege, medical-data privilege, or schema exposure was added. Signed-in admins also have no raw writes: the later admin module must add narrow, active-admin-authorized mutation functions rather than a generic write endpoint or exposing the server key.

| Internal table | Contract |
| --- | --- |
| `directory_specialties` | Canonical text slug ID (1–64 chars), en/ne labels, active flag. Empty initially: no guessed clinical taxonomy or automatic seeds. |
| `directory_providers` | UUID identity, type doctor/hospital/clinic; doctor identity is a unique FK to an existing doctor profile, validated by trigger. Hospitals/clinics are facility identities, without a new auth role/account. Public display name/phone/email/address, nullable numeric fee/currency; separate active, approval_status, verification_status, is_demo, publication_status. Private review_notes/verification_reference/reviewed_by/reviewed_at. Defaults inactive/pending/unverified/not-demo/draft; payment cannot change these. |
| `directory_provider_specialties` | Many-to-many provider ↔ specialty. |
| `directory_affiliations` | Many-to-many doctor provider ↔ hospital/clinic provider, unique pair; trigger validates identity types. Separate active/approval/demo flags and nullable facility-specific doctor fee/currency. No single-facility overwrite. |
| `directory_affiliation_specialties` | Many specialties offered by a doctor at a particular facility. A live doctor match requires that specialty on the doctor, affiliation AND facility. |
| `directory_entitlements` | Multiple paid periods per provider; plan listing/sponsored (sponsored includes listing); payment_status pending/paid/revoked, finite starts_at/ends_at, is_demo. Private unique nullable payment_reference and internal_notes. No gateway, payment checkout, currency pricing or self-service billing implemented. |

Known fee requires a nonnegative numeric amount and uppercase three-letter currency. Null amount remains unknown, never converted to zero or “free”; an explicit zero with currency is valid. No currency is assumed. Provider fee applies to hospital/clinic matches; doctor matches use affiliation fee with no guessed fallback. Currency format is checked, not a complete ISO currency registry. Foreign-key lookup columns have indexes; period and publication indexes support eligibility scans.

Verification is explicitly required for **all** live provider types; an active doctor account, saved row, approved listing, or payment alone is insufficient. This is a visibility gate, not a claim that the future verification process has been clinically validated. Evidence/reviewer fields remain private; professional checks and approval UI are later work. Affiliations require independent approval/activity and a separately eligible paid facility. These strict fail-closed choices establish Module 2's live paid directory; they do not change legacy ordinary booking, existing appointment records or medical sharing.

### Shared eligibility/query contract for later modules

Single source of truth: `private.get_eligible_directory_matches(text[], text, uuid)`, SECURITY DEFINER with empty search_path and an active stored-profile check against auth.uid(). The public `get_directory_matches` RPC is a SECURITY INVOKER wrapper returning the same public projection. EXECUTE is explicitly revoked from PUBLIC/anon and granted only to authenticated; existing authenticated private-schema USAGE permits calling the narrow helper but not reading any raw tables. Neither query accepts a caller identity, time, paid flag, verification flag or sponsorship flag.

RPC arguments:

```ts
{
  requested_specialty_ids: string[] | null,
  requested_provider_type: 'doctor' | 'hospital' | 'clinic' | null,
  requested_provider_id: string | null
}
```

Application entry point:

```ts
getDirectoryMatches({ specialtyIds?, providerType?, providerId? })
// Promise<{ data: DirectoryMatch[]; error: string | null }>
```

- Omitted specialties / SQL NULL = deliberate general browse. **Empty array = zero matches**, including sponsored listings. Unknown IDs never broaden the specialty. At most 20 requested specialty IDs; server helper validates slug IDs and UUID/provider type. SQL validates bounded filters independently.
- Provider must be active, approved, explicitly verified, not demo, published (not draft/suspended), with at least one paid non-demo entitlement covering **[starts_at, ends_at)** using statement_timestamp(). Doctor's underlying profile must still be active and role doctor.
- Doctor additionally needs an active, approved, non-demo affiliation to a facility passing the same provider/paid gates and the specialty intersection above. Unapproved affiliation or expired/unverified facility cannot appear through a paid doctor listing.
- `is_sponsored` is derived only from an in-period paid, non-demo sponsored entitlement on the matched provider. Both public disclosure strings are returned: `Sponsored · Paid placement` / `प्रायोजित · सशुल्क स्थान`. No clinical-quality claim or urgency/specialty manipulation. Results are alphabetic, not promoted by sponsorship; any later sponsored display must stay inside the returned relevant matches and display the disclosure.
- One row per provider/specialty/facility affiliation; preserve duplicates across legitimate relationships when grouping for UI. Public fields: provider_id/type, doctor_profile_id, display_name, public_phone/email/address, specialty_id/name_en/name_ne, affiliation_id, facility_id/name/phone/address, fee_amount/currency, is_sponsored and disclosure strings. Internal approval/reviewer/payment fields are never returned. Parser explicitly projects allowed keys even if an RPC response unexpectedly contains extra fields.
- Stable alphabetical result order, capped at 200 match rows; no pagination in Module 2. Filter by provider and specialty before inspecting a particular affiliation. Future booking must validate its selected affiliation against this shared authoritative rule inside the atomic booking transaction, avoiding a read-then-insert expiry race; do not duplicate eligibility in JavaScript.
- Existing getDoctors(), booking RPCs/actions, appointments tables, UI routes and mobile sections remain unchanged by Module 2. Later browse/booking modules must adopt this query deliberately. No symptom strings, urgency fields, clinical ranking or persistent chat data enter the directory schema.
